**M1 — Regex ticker di Worker menolak SEMUA ticker multichain (halaman per-ticker 30/43 rusak)**
- **Kategori:** inkonsistensi desain-vs-kode / UX
- **Bukti:** `api/worker.js`, route `/api/history` dan `/api/ticker`:
  ```js
  if (!ticker || !/^[A-Z0-9]+X$/.test(ticker)) return json({ error: ... }, 400);
  ```
  Regex mensyaratkan akhiran `X`. `TSLAr`.toUpperCase() = `TSLAR` → **tidak match** → 400. Sama untuk `NVDAc` (`NVDAC`), `TSLAB` (`TSLAB`), `SPYr` (`SPYR`). Hitung ulang: 43 ticker live − 13 xStocks = **30 dari 43 ticker** mengembalikan 400. `fetchTicker` melempar `API HTTP 400` → `web/src/app/ticker/[id]/page.tsx` menampilkan `load_error`. Home table (`/api/latest`, tanpa validasi) tetap jalan — jadi kerusakan tidak terlihat dari beranda.
- **Perbaikan:** ganti ke `^[A-Z0-9]{2,12}$` dan validasi keberadaan lewat `universe` (sudah ada di `loadTicker`), bukan lewat bentuk string. Tambah fixture QA: untuk tiap ticker di `universe`, `/api/ticker` harus 200.

**M2 — Outcome Monday Gap memakai 13:30 UTC hardcode; di EST bursa buka 14:30 UTC**
- **Kategori:** rumus/ambang
- **Bukti:** `poller.py`, `_monday_gap_fill_outcomes`:
  ```python
  mon_open = mon.strftime("%Y-%m-%dT13:30:00Z")
  ```
  13:30 UTC = 09:30 ET **hanya saat EDT**. DST AS 2026 berakhir 1 Nov; prediksi pertama jatuh Minggu 16 Nov (EST) → NYSE buka **14:30 UTC**. Kode mengambil `depth_weighted_price` pertama ≥ 13:30 UTC, yaitu harga ~08:30 ET — **satu jam sebelum open**. Definisi "gap aktual" yang di-pre-register §2.2 dilanggar sistematis sepanjang Nov–Mar.
- **Perbaikan:** hitung `mon_open` dari `ZoneInfo("America/New_York")` seperti helper lain di file yang sama (`in_tight_window`, `next_schedule_close_utc`) — konsisten, tidak perlu tabel DST.

**M3 — Confidence Monday Gap menghitung baris, bukan akhir pekan → saturasi +25 setelah SATU akhir pekan**
- **Kategori:** rumus/ambang
- **Bukti:** `poller.py`, `_monday_gap_predict`:
  ```python
  _c = query("SELECT COUNT(*) AS n FROM monday_gap WHERE outcome IN ('accurate','inaccurate')")
  calibrated = int(_c[0]["n"]) if _c else 0
  ```
  lalu `calib = 5 * max(0, min(int(calibrated_weekends or 0), 5))`.
  Desain §2.2: "+5 per **akhir pekan** terkalibrasi, maks 25 setelah **5 akhir pekan**". `COUNT(*)` menghitung baris ticker-minggu. Dengan 43 ticker, satu akhir pekan yang menghasilkan ≥5 baris langsung memberi `calib = 25` (maksimum). Bahkan harness (2 prediksi) memberi `calib = 10` setelah 1 akhir pekan. Hitung ulang: seharusnya `COUNT(DISTINCT week_start)` → 1.
- **Perbaikan:** `SELECT COUNT(DISTINCT week_start) AS n FROM monday_gap WHERE outcome IN ('accurate','inaccurate')`. Tambah guard: `calib == 5 * distinct_weekends`.

**M6 — Ambang funding 8× terlalu ketat: komponen praktis selalu 0**
- **Kategori:** rumus/ambang
- **Bukti:** `poller.py`, `exit_score_v1`:
  ```python
  pct = abs(funding) * 100.0
  if pct <= 0.01: comps["funding"] = 0.0
  elif pct >= 0.10: comps["funding"] = 15.0
  ```
  `funding` adalah rate **per interval (hourly)** apa adanya dari API (komentar kode sendiri mengakui: *"Hyperliquid publishes the rate per funding interval (hourly), while the design labels the component 'funding 8 jam'; no silent x8 scaling is applied"*). Hitung ulang: ambang desain 0,01%–0,10% **per 8 jam** setara **0,00125%–0,0125% per jam**. Dengan rate hourly, `pct = 0.00125` → **0 poin** (di bawah 0,01). Untuk mencapai 15 poin perlu funding 0,10%/jam = **2,4%/hari ≈ 876%/tahun** — praktis tidak pernah terjadi. Jadi komponen 15 poin itu mati, dan Exit Score maksimum realistis turun dari 100 ke 85 (atau bobot efektifnya 0).
- **Perbaikan:** revisi tertulis bertanggal (bukan penalaan diam-diam): kalikan ambang dengan 1/8 → `≤0,00125% → 0`, `≥0,0125% → 15`; **atau** pertahankan angka dan ubah label menjadi "per interval" dengan penjelasan eksplisit bahwa nilainya 8× lebih ketat dari maksud desain. Mana pun, harus ada catatan revisi — bukan komentar kode.

### SHOULD-FIX

**S1 — Migrasi tidak self-idempotent (klaim "idempotent" hanya benar untuk 3 dari 5 statement)**
- **Bukti:** `migrations/2026-11-12-penambahan.sql` akhir file:
  ```sql
  ALTER TABLE deviations ADD COLUMN exit_score REAL;
  ALTER TABLE deviations ADD COLUMN exit_score_version TEXT;
  ```
  Tanpa guard. Jalan kedua → `duplicate column name`. Header memerintahkan cek `PRAGMA` manual. `DIFF_RINGKAS.md` §3.3 menyebut "Satu file migrasi idempotent (klaim)"; `CHECKLIST_QA.md` B2 "TERUJI di sqlite lokal" — yang teruji adalah harness yang memeriksa dulu, bukan file migrasinya.
- **Perbaikan:** bungkus dua ALTER dalam runner Python kecil yang membaca `pragma_table_info` (pola `migrations/2026-11-09-pools-excluded.sql`), atau beri nama file `*.sql` + `apply_migration.py` yang idempotent. Jangan biarkan file bernama "migration" yang tidak bisa dijalankan dua kali.
